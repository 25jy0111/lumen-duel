# システム構成と設計方針

## 構成

```text
src/
  game/
    types.ts     状態・カード・行動の型（React依存なし）
    cards.ts     カード定義、効果、出現重み、定義参照
    engine.ts    初期化、行動検証、状態遷移、抽選、補充、勝敗
    cpu.ts       状態を受け取り行動を返す決定方針
  App.tsx        表示、選択状態、人間入力、CPU実行の予約
  App.css        レスポンシブ画面
  main.tsx       Reactエントリーポイント
  index.css      共通スタイル
  test/          Vitestのユニット・シミュレーションテスト
docs/rules.md    実装しているルールの正本
```

TypeScript + React + Vite。サーバー・DB・外部サービス不要。ゲーム状態はメモリ上だけに保持し、ページ再読み込みで新しいゲームになります。開発時のViteサーバーは静的アプリを配信するためのもので、対戦サーバーではありません。

## エンジンの境界

- `createGame(seed?)` が初期状態を返します。
- `getActingPlayer(state)` は現在入力すべき人を返します。防御中は攻撃側の `activePlayer` と異なるので、UIやCPUはこの関数を使います。
- `validateAction(state, actor, action)` はエラー文または `null` を返します。
- `applyAction(state, actor, action)` は検証後に `{ok:true,state}`、拒否時は `{ok:false,error,state}` を返します。
- 元の状態を書き換えません。不正な行動では抽選も進まず、入力状態をそのまま返します。
- `GameAction` は攻撃、防御、回復、祈る、捨てるという小さな判別可能unionです。UIとCPUはこの同じ境界を通します。
- `main → defense → main` が基本。回復・祈る・捨てるは `main → main`、致死ダメージなら `finished`。

状態と行動はJSONで表現でき、DOM・タイマー・通信に依存しません。UIのカード選択など、一時的な表示状態はReact側に分離します。CPU待機タイマーはReactのEffectのクリーンアップで解除し、再戦で前の試合の行動が混ざることを防ぎます。

## カードと効果

`CardDefinition` は種類・重み・MPコスト・効果データを持ちます。`CardInstance` は固有の `uid` と `definitionId` だけを持ち、同種の札を区別します。

現在の効果は `attack`、`defend`、`restore` の3種です。同じ効果体系のカードは `cards.ts` に定義を加えるだけで使えます。新しい効果は型とエンジンの効果処理・検証を追加します。種類固有の併用制限はエンジン、CPU戦術はCPUファイルで管理します。任意スクリプト実行や巨大な効果DSLは導入しません。

## 乱数と再現性

Mulberry32を使用し、32bit内部値を `GameState.rngState` に格納します。同じ初期seedと同じ行動列から同じ先攻・手札・補充を再現できます。カードの固有IDとログIDも状態内で採番します。

UIではブラウザの `crypto.getRandomValues` から初期seedを生成します。抽選は重み合計を使うため、カード追加時に百分率を再計算する必要はありません。対戦用の暗号学的な不正対策は未実装です。

## CPU

`chooseCpuAction(state, actor='cpu')` は状態を変えず行動を返すだけです。回復優先・攻撃力比較・防具の小さな部分和探索・祈り/破棄のフォールバックを実装します。シミュレーションでは同じ方針を人間側にも使います。ターン外や試合終了後の呼び出しは開発上の誤用として例外にします。

## テストと確認

- Vitest：攻防、資源上限、補充、奇跡、祈り・破棄、不正入力、ターン、勝敗、非破壊更新。
- 120個のseedで両者をCPU方針により対戦させ、毎行動の合法性、HP/MP/手札上限、終了を確認。
- TypeScript型検査とVite本番ビルド。
- ブラウザの操作確認は `scripts/browser-smoke.mjs`（既存Edgeを利用。手順はREADME）。

シミュレーションの終了確認はすべての乱数列・人間の選択での有限決着を証明するものではありません。祈りや防御なし応答により、合法な局面で入力不能にならない設計です。

## 後から拡張する場合

- 複雑な効果・確率・連鎖：現在の効果処理から小さな解決キューを抽出し、発生イベントを返す設計へ。描画中にエンジンを進めない。
- アニメーション：ログを基礎に、機械可読の戦闘イベントを遷移結果へ加える。UIがイベントを再生する。
- 複数人：現在は2人のIDと交代処理を明示的に実装。プレイヤー順と対象指定、脱落判定を導入するときに一般化する。
- オンライン：このエンジンをサーバー側で実行し、入力を検証。現在の完全な状態をそのまま配信せず、相手の手札・乱数状態を除いた公開ビューを作る。
- 独自ルール：現在の固定値を必要になった段階で設定化し、互換性・保存データのバージョンを検討する。
- アバター・演出：画面層へ追加。今はネットワーク、永続化、アカウントを実装しない。

第一段階は小さく動作することを優先します。現状が複数人通信に対応済みであるとは扱わないでください。
