## 実装済みの範囲

- TypeScript / React / Vite / Vitest、npmのlockfile、Git管理。
- 人間1人対CPU1人。先攻ランダム、HP40、MP10、所持金20、手札9枚、上限18枚。
- オリジナルの仮カード8種類。通常武器・追加武器・防具・奇跡・HP/MP回復雑貨。
- 通常武器1枚＋追加武器の攻撃、複数防具、攻防差ダメージ。
- 消費数と同数の補充。奇跡はMP消費、手札に残り、使用ごとに1枚ドロー（上限あり）。
- 使える攻撃・回復がないときだけ祈る。捨てるは補充せずターン終了。自由な手札交換なし。
- CPUの攻撃・回復・防御・祈り・手詰まり時の破棄。人間と同じエンジンを利用。
- 日本語UI、ステータス、手札選択、ログ、勝敗、新しいゲーム、PC/スマートフォン幅。
- カード種別ごとのオリジナルSVGアイコン。外部画像・フォントへの依存なし。
- 公開URLからインストール・ログイン不要で遊べる。ただし各端末で独立したCPU戦。

## 設計を引き継ぐときの要点

| ファイル | 担当 |
| --- | --- |
| `src/game/types.ts` | 状態・カード定義・行動の型 |
| `src/game/cards.ts` | ステータス、効果、相対的な出現重み |
| `src/game/engine.ts` | 初期化、検証、状態遷移、抽選、補充、勝敗 |
| `src/game/cpu.ts` | 状態から行動を選ぶだけのCPU方針 |
| `src/App.tsx` | 表示・人間入力・CPUの実行タイミング |
| `src/test/*.test.ts` | ルールとCPU、シード付き模擬対戦 |
| `scripts/browser-smoke.mjs` | ブラウザの実ボタン操作による対戦・再戦確認 |

エンジンはReact・DOM・通信に依存しない。`applyAction` は元の状態を変更せず、失敗した行動では乱数も進めない。CPUと画面は同じ `validateAction` / `applyAction` を使う。

`getActingPlayer` は防御中には防御側を返す。`activePlayer` は攻撃宣言時のプレイヤーのままなので、操作権判定に直接使わない。基本状態遷移は `main → defense → main`、致死ダメージで `finished`。

Mulberry32の乱数状態は `GameState.rngState` に保存され、同じseedと行動列で再現可能。カードを追加するときはデータ化された既存効果を活用し、新効果だけ必要な処理を増やす。まだ複雑な効果DSLや多人数用の汎用基盤はない。

## 自宅PCでの準備

必要なものはGit、Node.js（プロジェクト指定：22.12以上、24系推奨）、npm、ローカルファイルを扱えるCodex。すでにあるものを再インストールする必要はない。Codexの導入が必要なら [OpenAI公式CLI案内](https://learn.chatgpt.com/docs/codex/cli) を参照。

**コード・文書・Git履歴はGitHubから取得する。学校PCの会話セッションや実行中プロセスが引き継がれることは前提にしない。** この資料とプロンプトで必要な文脈を渡す。

既存の作業フォルダを調べ、まだ取得していない場合のみ、新しい専用フォルダへcloneする。

```sh
git clone https://github.com/25jy0111/lumen-duel.git
cd lumen-duel
npm ci
npm test
npm run build
npm run dev
```

通常の開発URLは `http://127.0.0.1:5173/`。ポート使用中は起動ログのURLを見る。

ビルド済みの確認は、別途 `npm run preview` で `http://127.0.0.1:4173/lumen-duel/`。GitHub Pages用の本番baseは `/lumen-duel/`、開発時は `/`。ここを誤って変更すると公開版で画像・JS・CSSが読めなくなる。

WindowsでPowerShellのスクリプト実行制限により `npm` が失敗する場合は、まず `npm.cmd` を使う。学校PCにあったNodeの絶対パスをコピーしない。Windowsでは通常のNode導入後に `start-game.cmd` でも起動できる。macOS/Linuxではnpmコマンドを使う。

## ブラウザテストの環境差

基本テストとビルドにブラウザは不要。`npm run test:browser` は別途起動中のゲームへアクセスする。

- スクリプトの既定ブラウザはWindowsの `C:/Program Files (x86)/Microsoft/Edge/Application/msedge.exe`。
- 自宅PCでこの場所がなければ、利用可能なChromium系ブラウザの実行ファイルを調べ、`BROWSER_PATH` に指定する。
- テスト先は `GAME_URL` で指定。既定は開発用 `http://127.0.0.1:5173/`。本番プレビューなら `/lumen-duel/` まで含める。
- GitHub Pagesの公開URLもテストできる。スクリーンショットは `test-results/` に出力され、Git管理外。
- テスト専用ブラウザで実行し、既存の個人ブラウザの認証情報をコピーする必要はない。
- ブラウザが使えないときは検証の制限を明記する。未実行を「成功」と報告しない。

## GitHubと学校・自宅の同期

- GitHubリポジトリはPublic。cloneと閲覧にログインは不要だが、pushには自宅PCでGitHubの書き込み認証が必要。
- CodexへのサインインとGitHubへのサインインは別。学校PCのGit認証・トークン・秘密鍵を資料やリポジトリへ保存して移さない。
- GitHub Pagesはすでに設定済み。自宅PCで設定し直したり、新しいリポジトリを作ったりする必要はない。
- `main` にpushするとActionsがテストとビルドを実行し、成功時に公開版を更新する。試作中は作業ブランチで進められる。
- 公開反映を依頼された場合は、検証・差分確認・commit・push・Actions結果・公開URLの確認まで行う。引き継ぎ確認だけで新しい機能を公開する必要はない。
- どちらのPCでも作業開始時に `git status`、`git fetch origin` を確認する。未コミット変更がなく、対象ブランチが `main` なら `git pull --ff-only` で最新を取得する。
- 作業終了時は依頼された範囲でcommit/pushし、別PCが取得できる状態にする。競合や分岐がある場合は内容を把握して統合し、force push・hard resetで片方を消さない。

学校PCの `tools/node`、GitHub設定用の一時スクリプト、`node_modules`、`dist`、スクリーンショット、Codexのスキル/プラグインはリポジトリに含まれない。これらを必須にせず、標準のGit・Node・npmで引き継ぐ。ゲーム内CPUには生成AIやOpenAI APIキーは不要。

## ユーザーとの進め方

- 日本語で、結果と操作手順を簡潔に説明する。ユーザーは細かな実装矛盾を見つける前提ではない。
- 細部は合理的に判断して実装し、設計案だけで終わらない。完成条件と必要な検証まで担当する。
- 質問を小出しにしない。本人の認証操作、重大なルール・方針変更など、本当に判断が必要なものだけまとめる。
- 認証などで本人の操作が必要でも、依存しない作業を先に終わらせてから、残りの操作と理由をまとめて伝える。
- 作業の最後に、変更点・検証結果・起動方法・制限・次の候補を報告する。
